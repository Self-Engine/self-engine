# Time tracker prior art: breaks, kinds of time, rounding, seconds, several projects, Pomodoro, the running timer

Research date: 2026-11-24.

Scope: how established time trackers store and compute these things, and which choices caused
known problems. Tools: Toggl Track, Harvest, Clockify, Kimai, Timing, Tyme, Timely, plus
Timewarrior, Watson, ActivityWatch, Timeular, Session and Pomofocus where they add something.

Source quality. Kimai's schema and logic come from its source code on GitHub (primary). Toggl,
Harvest and Clockify come from their API references and help centres. Harvest's help centre
(`support.getharvest.com`) refused automated fetches; claims from it rest on search-engine
excerpts of those pages and are marked "(excerpt)". Community forum threads are marked as such.
Anything not confirmed is marked **unverified**.

## Summary

1. **No tool examined stores a break as a stretch inside a time entry.** The patterns are: a
   separate entry flagged as a break (Clockify), a separate entry with a tag or label (Toggl), a
   gap between entries that reports read as a break (Tyme), a break-seconds number on the entry
   (Kimai, beta), or a negative-duration entry that overlaps a longer one (a Kimai plugin). A
   stretch inside one entry would be new ground; nobody's costs are on record for it.
2. **Rounding is computed on read almost everywhere.** Toggl, Clockify, Timing and Tyme leave the
   recorded entry untouched and round in reports. Harvest stores exact hours and exposes a
   derived `rounded_hours`; changing the account rule re-rounds all past entries in reports but
   not existing invoices (excerpt). Kimai is the exception: it overwrites begin, end and duration
   with rounded values when the entry is saved.
3. **Per-entry versus per-group rounding is the main source of "totals don't add up".** Clockify
   and Harvest round each entry and then sum. Toggl rounds each entry in ungrouped reports but
   sums first and rounds the subtotal in grouped reports, so the same data gives different totals
   by view.
4. **Seconds are stored by all the timer-based tools** (Toggl, Kimai, Timewarrior, ActivityWatch;
   Harvest stores decimal hours). The visible problems come from display: Clockify's `h:mm`
   format rounds each entry up to the next minute; Kimai documents that hours shown with two
   decimals do not multiply to the money shown, and offers a mode that rounds durations to 36-second
   steps to fix it.
5. **No tool lets one entry count for several projects with a defined division.** Every entry has
   exactly one project. Users split an entry at a point in time (Toggl, Clockify), or allow
   overlapping entries (Kimai setting), or put several tags on one entry, which counts the full
   duration under each tag. Toggl hides the grand total of tag-grouped reports for this reason.
6. **"Kind of time" is usually not a fixed enum on the entry.** Clockify has a `type`
   (`REGULAR`, `BREAK`, plus `HOLIDAY`, `TIME_OFF` generated by its time-off module). Kimai had a
   fixed `category` (`work`, `holiday`, `sickness`, `parental`, `overtime`) and deprecated it in
   2.45. Everything else uses a billable flag plus user-defined tags, activities or projects.
7. **Pomodoro produces one entry per work interval, and the break, if kept, is a separate entry.**
   Toggl's open-source desktop app stops the running entry at the interval end, trims it to
   exactly the interval length, and starts a new entry "Pomodoro Break" with tag `pomodoro-break`
   and no project. Clockify's extension logs breaks to a configurable "break project".
8. **The running timer is an entry without an end** in Kimai (`end_time` null), Harvest
   (`is_running`, `timer_started_at`), Timewarrior (interval without `end`). Toggl encodes it as a
   negative duration: in API v8 `-start_epoch`, in API v9 "preferably -1". Kimai allows a
   configurable number of simultaneous timers (default 1); Tyme lets the user choose parallel
   timers; Toggl, Watson and Harvest run one at a time.
9. **Pause is rare.** Toggl refuses it on the grounds that it needs constant server monitoring;
   Tyme has no pause button and offers "Cluster mode" that merges stop/starts of one task per day
   into one duration-only entry; Harvest's "restart" adds to the same entry on duration accounts
   (`hours_without_timer`) but creates a new entry on timestamp accounts. Clockify and Toggl
   "continue" creates a new entry.
10. **Idle and forgotten timers are handled by asking the user**, with the same four choices
    across tools: keep, discard and stop, discard and continue (new entry), or put the idle time
    into its own new entry. Kimai additionally rejects stopping a record above a maximum duration
    (default 8 hours in its docs).

## 1. Breaks

| Tool                          | How a break is stored                                                                                                  | What reads it                                                   |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Clockify                      | A normal time entry with `type: BREAK`; needs a project; admins can convert entries between break and regular          | Reports filter by break status; billable breaks can be invoiced |
| Toggl Track                   | No break concept; a separate entry named "Break" or similar, or the Pomodoro break entry tagged `pomodoro-break`       | Whatever the user's tags/projects say                           |
| Kimai                         | `break` column on the timesheet row, integer seconds; duration = end − begin − break; feature in beta                  | Duration and therefore money and exports                        |
| Kimai + Deduction-Time plugin | A separate entry on an activity marked "deduction time", whose duration is made negative; requires overlapping entries | Exports and invoices subtract it                                |
| Tyme                          | Not stored. Any gap between two entries within a configured min/max length is shown as a break in reports              | Reports only                                                    |
| Harvest                       | No break concept found (**unverified**)                                                                                | —                                                               |
| Timing                        | Not researched in depth (**unverified**)                                                                               | —                                                               |

Details and sources:

- Clockify stores breaks as their own entries. Break mode is switched on per workspace by an
  admin, is a paid feature, and "you need to select a project for the break before the break
  timer can start"
  ([Clockify: breaks on web](https://clockify.me/help/track-time-and-expenses/breaks-web)). Only
  admins and owners can "Mark as break" or "Mark as regular entry" (same page). Breaks are
  "kept separate from your billable work hours" and reports filter by break status; billable
  breaks can be invoiced
  ([Clockify: breaks](https://clockify.me/help/extra-features/break)). On a kiosk, starting a
  break clocks the person out and finishing it clocks them back in (same page). A forum user
  reports that creating a `BREAK` entry through the API still started a normal timer
  ([forum](https://forum.clockify.me/t/how-to-run-the-timer-in-break-mode/3300)).
- Toggl has no dedicated break tracking; a community answer recommends "creating a separate time
  entry labeled something like 'Break' or 'Lunch'"
  ([community](https://community.toggl.com/t/tracking-breaks-on-toggl-track/4941)).
- Kimai's timesheet entity has `break` as "Break duration for this record in seconds, can be
  null", and `getCalculatedDuration()` returns end − begin − break
  ([Timesheet.php](https://github.com/kimai/kimai/blob/main/src/Entity/Timesheet.php)). The
  setting "Activates break time tracking (a beta feature of Kimai)"
  ([configurations](https://www.kimai.org/documentation/configurations.html)). The cloud changelog
  of August 2025 adds a `break` column to export and importer
  ([Cloud-Update 122](https://www.kimai.org/en/changelog/2025/cloud-update-122)). The break
  number has no position in time: the entry knows how long the break was, not when.
- The Kimai Deduction-Time plugin works the other way: a "break time" activity whose entries get
  a negative duration, recorded alongside a whole-day attendance entry, with overlapping records
  allowed. The negative value "is not used in the UI and not saved"; it is computed as end −
  start and negated
  ([Deduction-Time Bundle](https://www.kimai.org/en/store/keleo-deduction-time-bundle.html)).
- Tyme: "Any gap between two entries that falls within the minimum and maximum break length" is
  shown as a break; settings are under Working Hours > Breaks
  ([Tyme FAQ](https://www.tyme-app.com/en/faq/)).

Costs seen:

- A break as its own entry (Clockify, Toggl) needs a project or a convention, and each report
  must decide whether to include it. Clockify made breaks a typed entry and then had to add
  conversion permissions and a report filter.
- A break number (Kimai) is cheap to compute with but loses where the break was; Kimai shipped
  it late and still as beta. The plugin route (negative overlapping entries) shows the demand
  for a break with a position in time, at the cost of overlaps and negative durations.
- A gap (Tyme) costs nothing to store but depends on thresholds; a long gap is "not working",
  not a break.

## 2. Kinds of time

| Tool                                 | Mechanism                                                                                 | Fixed or user-defined        | What reads it               |
| ------------------------------------ | ----------------------------------------------------------------------------------------- | ---------------------------- | --------------------------- |
| Clockify                             | `type` on the entry: `REGULAR`, `BREAK`; `HOLIDAY`, `TIME_OFF` created by time-off module | Fixed                        | Reports, kiosk, time off    |
| Clockify, Toggl, Harvest, Kimai      | `billable` boolean on the entry                                                           | Fixed (one flag)             | Invoices, billable reports  |
| Kimai                                | `category` string: `work`, `holiday`, `sickness`, `parental`, `overtime`                  | Fixed; deprecated since 2.45 | Working-time features       |
| Kimai                                | Activity per entry (required), plus tags                                                  | User-defined                 | Rates, reports              |
| Toggl, Clockify, Timewarrior, Watson | Tags                                                                                      | User-defined, many per entry | Report grouping and filters |
| Timing                               | Billing status: billable, billed, paid (2025.8)                                           | Fixed                        | Report filters              |

- Clockify's type enum: third-party API mirrors list `REGULAR` and `BREAK` as request values and
  `REGULAR`, `BREAK`, `HOLIDAY`, `TIME_OFF` as response values. I could not read the official
  reference page in full, so the exact enum is **unverified**. Clockify's own help confirms
  holiday and time-off entries are created automatically from approved requests and marked with
  their own icon
  ([Clockify: holidays and time off](https://clockify.me/help/track-time-and-expenses/track-holidays-time-off)).
- Kimai's constants `WORK`, `HOLIDAY`, `SICKNESS`, `PARENTAL`, `OVERTIME` are all marked
  deprecated since 2.45 and `setCategory()` raises a deprecation; the column `category`
  (string, default `work`) remains. Kimai's `billable` is a boolean column, with `BILLABLE_AUTOMATIC`,
  `YES`, `NO`, `DEFAULT` as form choices
  ([Timesheet.php](https://github.com/kimai/kimai/blob/main/src/Entity/Timesheet.php)). Why the
  category was deprecated is **unverified**.
- Kimai: "Non-billable timesheets are excluded from invoices and budget calculations"
  ([timesheet docs](https://www.kimai.org/documentation/timesheet.html)).
- Toggl: `billable` is optional, default false; tags are names, created on the fly
  ([Toggl API v9](https://engineering.toggl.com/docs/track/api/time_entries/)).
- Harvest: `billable` on each entry
  ([Harvest API](https://help.getharvest.com/api-v2/timesheets-api/timesheets/time-entries/)).
- Timing: billing status tracking with billable, billed and paid, and a default for new entries
  ([TidBITS on Timing 2025.8](https://tidbits.com/watchlist/timing-2025-8/)).
- Toggl's Pomodoro break uses a tag (`pomodoro-break`), not a kind (see section 6).

Costs seen: a fixed enum gets read by many modules and is hard to change (Kimai kept the column
but deprecated the values). Tags are flexible but carry no meaning a report can rely on, and
counting by tag double-counts entries that carry several tags (section 5).

## 3. Rounding

| Tool               | Rules                                                                                                                           | Applies per                                       | Stored or computed                                       | Where the rule lives                                   | Rule change affects old entries                                    |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------ |
| Toggl              | up, nearest, down; 1, 5, 6, 10, 12, 15, 30 min, 1 h, 4 h                                                                        | Entry when ungrouped; group subtotal when grouped | Computed in reports                                      | Report setting                                         | Yes, it is a view                                                  |
| Clockify           | up, nearest, down; 1 min to 1 h                                                                                                 | Entry, then summed                                | Computed in reports and exports; money uses rounded time | Workspace (admin)                                      | Yes, it is a view                                                  |
| Harvest            | nearest, or up, to 6, 15, 30 min                                                                                                | Entry, then summed                                | Exact `hours` stored; `rounded_hours` derived            | Account-wide                                           | All past entries in reports; existing invoices unchanged (excerpt) |
| Kimai              | Separate intervals for begin, end, duration; modes default (begin down, end and duration up), closest, floor, ceil; per weekday | Entry                                             | **Stored**: begin, end and duration overwritten on save  | System settings; plugin adds customer/project/activity | Only entries saved after the change (inferred from code)           |
| Kimai decimal mode | Duration to 36-second steps (0.01 h)                                                                                            | Entry                                             | Stored duration                                          | System settings                                        | As above                                                           |
| Tyme               | Per task; project default inherited by new tasks                                                                                | Entry totals                                      | Computed; recorded start and end unchanged               | Task (project default)                                 | Locked once the task is completed                                  |
| Timing             | up, down, nearest; 1, 5, 6, 10, 12, 15, 30 min, 1 h                                                                             | Entry (**unverified**)                            | Computed; hover shows original                           | Report                                                 | Yes, it is a view                                                  |
| Timely             | No rounding; "tracks the precise number of hours, minutes, and seconds"                                                         | —                                                 | —                                                        | —                                                      | —                                                                  |

Details and sources:

- Toggl: three methods and the interval list; "Rounding is applied at the report level — it never
  edits or overwrites your original time entries"; ungrouped entries are rounded "on its own,
  separately from any others", while grouped reports first add "all entries in a group or
  sub-group exactly as tracked, then rounds that combined total"
  ([Toggl docs: rounding](https://docs.toggl.com/rounding),
  [support article](https://support.toggl.com/en-us/article/rounding-46d8m9)). Rounding is a
  paid feature (same).
- Clockify: "Time rounding only affects how durations of time entries appear in reports and
  exports"; per entry, then summed; with rounding on, "Clockify calculates billable amounts using
  the rounded time entries"; entries cannot be edited in the Detailed report while rounding is on
  ([Clockify: time rounding](https://clockify.me/help/extra-features/time-rounding)).
- Harvest: `rounded_hours` is "used in summary reports and invoices", rounded per the account's
  Time Rounding preference
  ([Harvest API](https://help.getharvest.com/api-v2/timesheets-api/timesheets/time-entries/)).
  Changing the setting "will apply the rounding setting you choose to all time entries for the
  account. Existing invoices will not be affected", and each entry is rounded before totalling
  ([Harvest: how does time rounding work](https://support.getharvest.com/hc/en-us/articles/360053116772),
  excerpt). Harvest's own help pages disagree on whether timesheets and the detailed report show
  rounded values (excerpt, same article and
  [why totals differ](https://support.getharvest.com/hc/en-us/articles/26871204446349-Why-are-the-totals-for-my-time-entries-different-in-different-places-in-my-account)).
  Harvest has rounded per entry since at least 2010
  ([blog 2010](https://www.getharvest.com/blog/2010/01/rounding-up-incremental-billing)).
- Kimai stores the rounded values. `DurationCalculator::calculate()` sets the duration from
  end − begin − break and then calls `applyRoundings()`
  ([DurationCalculator.php](https://github.com/kimai/kimai/blob/main/src/Timesheet/Calculator/DurationCalculator.php));
  the rounding classes call `setBegin()`, `setEnd()`, `setDuration()` on the entity
  ([DefaultRounding.php](https://github.com/kimai/kimai/blob/main/src/Timesheet/Rounding/DefaultRounding.php));
  the calculators run in a Doctrine `onFlush` listener on insert and update, which recomputes the
  change set "so the calculated values are persisted"
  ([TimesheetSubscriber.php](https://github.com/kimai/kimai/blob/main/src/Doctrine/TimesheetSubscriber.php)).
  The weekday of the **end** decides which rules apply, and several matching rules all apply in
  turn ([RoundingService.php](https://github.com/kimai/kimai/blob/main/src/Timesheet/RoundingService.php)).
  Rounding applies only to stopped records
  ([configurations](https://www.kimai.org/documentation/configurations.html)). Consequence
  (inferred, not stated in docs): the measured start and end are lost once rounded, and a rule
  change touches only entries saved later. A third-party plugin moves duration rounding to
  customer, project or activity level
  ([Glorpen duration bundle](https://www.kimai.org/en/store/glorpen-duration-bundle.html)).
- Kimai's rate rounding: in "classic" mode it computes with unrounded seconds and shows hours
  with two decimals, and warns of a "mismatch between displayed duration and monetary total"; the
  "decimal" mode rounds durations to 36-second steps so "displayed duration × hourly rate =
  displayed amount" ([Kimai: rounding](https://www.kimai.org/documentation/rounding.html)).
- Tyme: "Rounding is applied when the totals of individual entries are calculated"; "Your
  recorded start and end times stay unchanged"; a completed task's rate and rounding can no longer
  change ([Tyme FAQ](https://www.tyme-app.com/en/faq/)).
- Timing: methods and intervals; "you can hover over duration and timespan columns to see the
  original values"; "Timing will also warn you if rounding causes overlapping timespans between
  entries" ([Timing: reports and export](https://timingapp.com/help/4-reports-and-export)).
- Timely does not round: "Time doesn't get rounded off"
  ([Timely blog](https://www.timely.com/blog/the-ultimate-guide-to-time-clock-rounding/), a
  vendor blog, not product docs).

Costs seen:

- Read-time rounding keeps the truth but makes totals depend on the view (Toggl grouped vs
  ungrouped) and makes old reports change when the rule changes (Harvest). Harvest protects
  invoices by freezing the invoice, not the entries; Tyme does it by locking the task.
- Write-time rounding (Kimai) gives stable numbers but destroys the measured times and needs
  care with running entries (Kimai skips them) and with which day decides the rule.
- Rounding start and end to clock blocks can create overlaps (Timing warns) and needs a rule for
  the day boundary (Kimai uses the end).

## 4. Seconds

| Tool          | Stored                                                                               | Shown / entered                                                      |
| ------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| Toggl         | `start`, `stop` as UTC timestamps to the second; `duration` integer seconds          | h:mm:ss in timer                                                     |
| Kimai         | `start_time`, `end_time` datetimes; `duration`, `break` integer seconds              | Input as `2:30`, `2.5`, `2h30m`                                      |
| Clockify      | Start and end timestamps (**unverified** precision)                                  | Full `hh:mm:ss`, compact `h:mm`, decimal `h.hh`, a workspace setting |
| Harvest       | `hours` as decimal hours; timestamp accounts also store `started_time`, `ended_time` | HH:MM or decimal                                                     |
| Timewarrior   | ISO UTC to the second, e.g. `20160405T162205Z`                                       | —                                                                    |
| ActivityWatch | `timestamp` UTC, `duration` float seconds                                            | —                                                                    |

- Toggl v9: start "Format: 2006-01-02T15:04:05Z"; if both stop and duration are sent they must
  satisfy start + duration = stop
  ([Toggl API v9](https://engineering.toggl.com/docs/track/api/time_entries/)); v8: "time entry
  duration in seconds"
  ([Toggl API v8](https://github.com/toggl/toggl_api_docs/blob/master/chapters/time_entries.md)).
- Kimai: duration and break in seconds
  ([Timesheet.php](https://github.com/kimai/kimai/blob/main/src/Entity/Timesheet.php)); duration
  input formats ([timesheet docs](https://www.kimai.org/documentation/timesheet.html)); with
  rounding at 0, "exact times, including seconds, are used"
  ([configurations](https://www.kimai.org/documentation/configurations.html)).
- Clockify: in `h:mm`, "time entry will be rounded up to a minute", so 00:01:15 shows as 0:02
  ([Clockify: duration format](https://clockify.me/help/track-time-and-expenses/duration-format)).
  Clockify is changing decimal mode to keep "the full duration of every time entry in
  calculations" and round to two decimals only for the displayed total
  ([Clockify: decimal duration format beta](https://clockify.me/help/track-time-and-expenses/decimal-duration-format-beta)).
  This is a known fix for sums of per-entry rounded displays.
- Harvest: `hours` is "Number of (decimal time) hours"
  ([Harvest API](https://help.getharvest.com/api-v2/timesheets-api/timesheets/time-entries/)).
  Harvest has a help page on why totals differ across places in the account
  ([Harvest: why totals differ](https://support.getharvest.com/hc/en-us/articles/26871204446349-Why-are-the-totals-for-my-time-entries-different-in-different-places-in-my-account),
  title only; content **unverified**).
- Toggl: billable amounts in the summary report may not match the total because amounts are
  rounded up to two decimals
  ([Toggl support](https://support.toggl.com/why-dont-my-summary-reports-billable-amounts-match-the-total)).
- Timewarrior ([extension API](https://timewarrior.net/docs/api/)) and ActivityWatch
  ([buckets and events](https://docs.activitywatch.net/en/latest/buckets-and-events.html)).

Costs seen: every "totals don't add up" complaint found traces to rounding each row for display
(minutes, two-decimal hours, two-decimal money) and then summing the rounded rows. Storing
seconds is not the problem; summing displayed values is. Kimai's 36-second step is one way to
make hours × rate match the money exactly.

## 5. One recording for several projects

No examined tool lets one entry belong to several projects with a defined split. Each entry has
one project (Toggl, Clockify, Harvest, Kimai require or allow exactly one; Watson takes one
project per frame plus tags
([Watson commands](https://github.com/jazzband/Watson/blob/master/docs/user-guide/commands.md))).
What users do instead:

- **Split at a point in time.** Toggl: split from the entry menu, entries over 10 minutes, a
  paid feature
  ([Toggl: list view](https://support.toggl.com/tracking-time-in-list-view), excerpt). Clockify:
  "Enter a specific time in the Split at box"; segments "retain all the original information"
  and are then edited one by one
  ([Clockify: split](https://clockify.me/help/time-tracking/split-time-entries)). Neither splits
  proportionally.
- **Overlapping entries.** Kimai has a setting to allow overlapping records (named in the
  [Deduction-Time Bundle page](https://www.kimai.org/en/store/keleo-deduction-time-bundle.html)).
  Two overlapping entries count in full for both projects; there is no division.
- **Several tags on one entry.** Timewarrior: "A tracked interval may have any number of
  associated tags" ([Timewarrior tags](https://timewarrior.net/docs/tags/)). Toggl counts an
  entry with two tags once under each tag, so the tag-grouped report hides the grand total and
  shows a non-duplicated total at the top instead
  ([Toggl support](https://support.toggl.com/why-are-grand-totals-hidden-when-i-group-a-report-by-tag-or-user-group),
  excerpt).
- **Run parallel timers.** Kimai allows more than one running entry by setting; Tyme lets "several
  tasks run in parallel" (section 7). This again counts full time for each.

Costs seen: full counting for each project inflates totals (Toggl's hidden grand total). A split
at a point in time is honest but loses the fact that the time served both. A proportional split
(for example 50/50 or by weight) would be new ground; I found no tool that does it, so its
reporting and rounding costs are not on record.

## 6. Pomodoro

| Tool                        | Work interval                                                                                    | Break                                                                                       | Overrun                                 |
| --------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- | --------------------------------------- |
| Toggl desktop (open source) | Running entry stopped at interval end                                                            | Optional new entry "Pomodoro Break", tag `pomodoro-break`, no project                       | Trimmed to exactly the interval length  |
| Toggl extension / mobile    | Pomodoro alarm on the running entry                                                              | Community reports a "Track Breaks as Time Entries" option (**unverified** in official docs) | **unverified**                          |
| Clockify extension          | Settings for interval, short and long break, "Long break starts after"; optional auto start/stop | Logged to a configurable default break project or the last used project                     | **unverified**                          |
| Session (macOS)             | Session with an intention and a category                                                         | **unverified**                                                                              | Timer can run past its length (reviews) |
| Pomofocus                   | Counted in pomodoros ("1 = 25min of work"); reports in focus hours                               | **unverified**                                                                              | **unverified**                          |

- Toggl desktop's `displayPomodoro()`: when the running entry reaches `pomodoro_minutes * 60`
  seconds it calls `Stop()`, then `SetDurationInSeconds(pomodoroDuration)` and
  `SetStopTime(start + pomodoroDuration)`; if `pomodoro_break` is set it starts a new entry with
  description "Pomodoro Break", project 0 and tag `pomodoro-break`
  ([context.cc](https://github.com/toggl-open-source/toggldesktop/blob/master/src/context.cc);
  settings `pomodoro`, `pomodoro_break`, `pomodoro_minutes`, `pomodoro_break_minutes` in
  [settings.h](https://github.com/toggl-open-source/toggldesktop/blob/master/src/model/settings.h)).
  So the stored record is one entry per work interval, and the break is optional and outside any
  project. Users ask for the break to land in the same project
  ([community](https://community.toggl.com/t/track-pomodoro-breaks-in-same-category-as-work-sessions/1754)).
- Toggl: Pomodoro settings are per app and not synced; conflicting settings "can cause problems
  with running timers"; not available in the web app
  ([Toggl: enable the Pomodoro timer](https://support.toggl.com/how-to-enable-the-pomodoro-timer)).
- Clockify: interval and break settings per platform
  ([Clockify: idle detection and reminders](https://clockify.me/help/track-time-and-expenses/idle-detection-reminders));
  the extension's "Default break project" setting
  ([Clockify: browser extension](https://clockify.me/help/apps/browser-extension), excerpt).
- Session: intention per session and categories
  ([App Store listing](https://apps.apple.com/us/app/session/id1521432881); details from user
  reviews). Pomofocus: [pomofocus.io](https://pomofocus.io/).
- Timeular has a reminder to take a break after X minutes of tracking, not a Pomodoro record
  ([Timeular 3.7 notes](https://support.timeular.com/en/articles/4665007-3-7)).

Costs seen: trimming the entry to the interval (Toggl desktop) rewrites what was measured.
Per-app Pomodoro state that is not stored causes sync problems (Toggl's warning). A break entry
without a project is invisible in project reports, which users then ask to change.

## 7. The running timer

| Tool        | What is stored while running                                                                        | Pause                                                                                | Several at once                                              | Forgotten / idle                                                                                                   |

Details and sources:

- Toggl v9: "For running entries should be negative, preferable -1"; stop via
  `PATCH .../time_entries/{id}/stop`, 409 if already stopped
  ([Toggl API v9](https://engineering.toggl.com/docs/track/api/time_entries/)). Toggl v8: the
  negative value denotes "the start of the time entry in seconds since epoch", and "The correct
  duration can be calculated as current_time + duration"
  ([Toggl API v8](https://github.com/toggl/toggl_api_docs/blob/master/chapters/time_entries.md)).
  The change from an encoded start to a sentinel `-1` shows the encoded form was not worth
  keeping once `start` is its own field.
- Toggl on pause: "tracking pauses and resumes would require constant monitoring by our
  servers", which "would, in turn, negatively affect our service's performance"; instead, similar
  entries are grouped in the timer list and reports
  ([Toggl: pause](https://support.toggl.com/does-toggl-have-a-pause-feature)).
- Toggl desktop idle actions: `DiscardTimeAt(..., split_into_new_entry)` with analytics names
  `idle-as-new-entry` and `discard-and-stop`, and `DiscardTimeAndContinue()` which discards and
  then calls `Continue()`
  ([context.cc](https://github.com/toggl-open-source/toggldesktop/blob/master/src/context.cc));
  setting `stop_entry_on_shutdown_sleep`
  ([settings.h](https://github.com/toggl-open-source/toggldesktop/blob/master/src/model/settings.h)).
- Harvest fields `is_running`, `timer_started_at` ("if tracking by duration"),
  `hours_without_timer` ("hours already tracked in this time entry, before the timer was last
  started"); restart only if not running
  ([Harvest API](https://help.getharvest.com/api-v2/timesheets-api/timesheets/time-entries/)).
  On timestamp accounts "timers cannot be restarted. Instead, a new timer will be created" (Harvest
  API v2 docs, excerpt via search). "Harvest only auto-stops other running timers on the same
  day", so a timer left on an earlier date survives new starts
  ([Harvest: stuck timer](https://support.getharvest.com/hc/en-us/articles/47201092522509-Stopping-a-stuck-or-runaway-timer),
  excerpt). Harvest also blocks invoicing, approval and archiving while a timer runs
  ([Harvest help title](https://support.getharvest.com/hc/en-us/articles/360048687651-Why-can-t-I-invoice-approve-or-archive-items-when-a-timer-is-running);
  content **unverified**).
- Clockify idle options and auto-stop triggers
  ([Clockify: idle detection and reminders](https://clockify.me/help/track-time-and-expenses/idle-detection-reminders));
  over-8-hour alert, and timers that cannot stop because required fields are empty or the
  timesheet is locked
  ([Clockify: can't stop the timer](https://clockify.me/help/troubleshooting/cant-stop-the-timer),
  excerpt).
- Kimai: "Permitted number of simultaneously running time entries" defaults to 1; starting a new
  one then stops the current one; above 1 the user must stop one manually. "Maximum duration of a
  timesheet record" in minutes rejects further updates or stops
  ([configurations](https://www.kimai.org/documentation/configurations.html)). `end_time` null
  for running records; `setEnd(null)` resets duration and rate to 0; "Do not rely on the results
  of this method for running records"
  ([Timesheet.php](https://github.com/kimai/kimai/blob/main/src/Entity/Timesheet.php)). Stopping
  can be refused for exported entries or durations above the maximum
  ([timesheet docs](https://www.kimai.org/documentation/timesheet.html)).
- Tyme: no pause button, Cluster mode, single or parallel timers, idle default 30 minutes
  ([Tyme FAQ](https://www.tyme-app.com/en/faq/)).
- Timewarrior: an interval without `end` is active, and "Any active interval is not necessarily
  the last element in the array" ([Timewarrior API](https://timewarrior.net/docs/api/)).
- Watson: one project at a time unless `stop_on_start` stops the running one
  ([Watson commands](https://github.com/jazzband/Watson/blob/master/docs/user-guide/commands.md)).
- ActivityWatch has no timer; it merges heartbeats with identical data within a `pulsetime`
  window into one event ([buckets and events](https://docs.activitywatch.net/en/latest/buckets-and-events.html)).

Costs seen:

- Storing the running timer in the entry table (all tools) means every computation must skip or
  special-case it: Kimai's duration is 0 and rounding is skipped; Toggl's duration is negative;
  Harvest blocks invoicing while one runs.
- Pause as "continue in a new entry" (Toggl, Clockify) fragments the record and forces grouping
  in the list. Pause as "add to the same entry" (Harvest duration accounts, Tyme Cluster) keeps one
  entry but loses start and end. No tool found keeps one entry with its pauses as positioned
  stretches.
- Forgotten timers are handled by prompts, alerts and maximum durations, not by the data model.
  Harvest's same-day-only auto-stop is a documented trap.

## What bears on which ticket

### Time kinds (#399)

- Only Clockify puts a fixed kind on the entry (`REGULAR`, `BREAK`, plus generated `HOLIDAY`,
  `TIME_OFF`). Cost: conversion permissions, a report filter, and an API that reportedly ignored
  the type on create.
- Kimai shipped a fixed `category` enum and deprecated its values in 2.45 while keeping the column.
  A fixed enum is hard to retire once stored.
- Most tools separate "billable" (one boolean) from "what kind of work" (user-defined tags,
  activities, projects). Billable is what invoices read.
- Option: a fixed small set of kinds that reports and billing read, with user-defined labels
  elsewhere. Option: kinds as user-defined rows. The second is the tag model, whose cost is that
  reports cannot rely on meaning.

### Seconds (#400)

- Toggl, Kimai, Timewarrior store whole seconds; ActivityWatch stores float seconds; Harvest stores
  decimal hours.
- Mismatched totals come from summing per-row rounded display values: Clockify `h:mm` rounds each
  entry up to the minute; Kimai's two-decimal hours do not match money. Clockify's fix: compute
  on full durations and round only the displayed total.
- Kimai's decimal mode (36-second steps) is an option if displayed hours × rate must equal the
  displayed amount exactly. Cost: the stored duration is no longer the measured one.

### Stretches (#402)

- No tool stores a break as a positioned part inside an entry. Patterns: separate break entry
  (Clockify, Toggl), gap read as break (Tyme), break seconds on the entry (Kimai, beta),
  negative overlapping entry (Kimai plugin).
- Kimai's break number loses where the break was; the plugin's overlapping negative entry exists
  because users wanted the position. Stretches inside the entry would give both, without
  overlaps or negative durations, but there is no prior art for their costs.
- Pause in other tools produces either new entries (Toggl, Clockify) or a merged duration
  without times (Harvest, Tyme Cluster). Stretches would cover pause too.

### Rounding (#403)

- Most tools round on read and keep measured data (Toggl, Clockify, Timing, Tyme, Harvest via
  derived `rounded_hours`). Kimai rounds on write and overwrites begin and end.
- With a stored Booked Duration, the question each tool answered differently is what happens on
  a rule change: Harvest re-rounds all past entries in reports and protects issued invoices;
  Tyme locks rounding when the task is completed; Kimai only affects entries saved afterwards.
- Per entry versus per group: Clockify and Harvest round per entry then sum; Toggl rounds group
  subtotals when grouped. Per entry is what a stored per-entry number implies; it inflates totals
  with many short entries (Timing's warning for app-usage entries).
- Rule location seen: report (Toggl, Timing), workspace (Clockify), account (Harvest), system
  plus weekday (Kimai), task with project default (Tyme), customer/project/activity (Kimai
  plugin).
- Rounding start and end to clock blocks (Kimai) creates overlaps (Timing warns) and needs a day
  rule (Kimai uses the end's weekday).

### Several projects on one Time Entry (#404)

- No tool found supports it. Users split at a point in time (Toggl, Clockify), allow
  overlapping entries (Kimai), run parallel timers (Kimai, Tyme), or tag several projects.
- Counting the full time for each project inflates totals; Toggl hides the grand total of
  tag-grouped reports for this reason.
- A proportional split would be new ground. Open costs: how the shares round so they add up to
  the Booked Duration, and what reports show as "total".

### The running timer (#405)

- Toggl went from encoding the start in a negative duration (v8) to a sentinel `-1` (v9).
  Kimai and Harvest use an entry without an end plus flags. All of them then special-case running
  rows in computations, rounding and invoicing.
- Simultaneous timers: one in Toggl, Watson; configurable in Kimai (default 1) and Tyme. Harvest
  auto-stops only same-day timers, which leaves old-day timers running.
- Pause: Toggl declined it (server monitoring cost, not an issue for a local app). Harvest's
  restart accumulates into one entry (`hours_without_timer`) on duration accounts.
- Forgotten and idle time: the common prompt set is keep, discard and stop, discard and continue,
  idle as new entry (Toggl desktop, Clockify). Kimai adds a maximum duration that blocks stopping.
  Clockify alerts after 8 hours and can stop on lock or sleep.

### Pomodoro (#406)

- Toggl desktop: one entry per work interval, trimmed to the exact interval length; the break is
  an optional separate entry with a tag and no project. Users ask for the break in the same
  project.
- Clockify: breaks go to a configured break project or the last used one.
- Pomodoro state kept per app and not stored caused sync problems in Toggl.
- Options: one entry per interval (Toggl), or one entry per session with breaks as stretches.
  The second has no prior art found; its cost is that the session's work and break time must be
  read from stretches rather than entries.
